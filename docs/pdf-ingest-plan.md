## 0. 结论先行（六句话）

1. 库选 **PyMuPDF 单库**，不引入 pdfplumber。表格结构化首版不做。
2. 解析放**独立 worker 子进程**，不放主进程——固定开销 117 MB，且 C 层崩溃会拖垮整个服务。
3. 「损坏 vs 空文档」用 `doc.is_repaired` 判定，**不要用「文本是否为空」**（实测已推翻后者）。
4. 双栏必须做 words 级行内切段，朴素 `get_text()` 在交错内容流上**实测串行**。
5. 乱码检测**不能只靠 U+FFFD**——编码失配时 U+FFFD 计数为 0。
6. 前端零新增依赖，PDF 抽取产物直接喂给现有 `ExcerptView` 的划词流程。

## 2. 逐条回答

### 【A】库选型：PyMuPDF，不引入 pdfplumber

**建议**：只用 PyMuPDF，走 `get_text()` 文本路径。

**理由**
1. 速度：六样本合计 0.06s vs 0.28s（快 4.7×）；500 页 0.35s vs 1.86s（快 5.3×）。
2. 内存：500 页 208.4 MB vs 259.7 MB（少 51 MB）。
3. 字符量：66078 vs 65978，多 100 字（+0.15%）；六样本逐一比对都是 +1 字符的固定模式，中文字符 round-trip 无损。
4. 依赖面：pdfplumber 拖入 `pdfminer.six` + `Pillow`，打包体积和 hidden-import 都增加；PyMuPDF 是单包。
5. 异常语义：损坏件 PyMuPDF 抛 `FileDataError`（明确指向文件数据），pdfplumber 抛 `PdfminerException`（封装层，信息更少）。

**why not pdfplumber**：它唯一的优势是 `find_tables()` 比 PyMuPDF 便宜 238×（1.89s vs 100.83s）。
但【D】首版不做表格结构化，这个优势用不上。为它多背 51 MB 内存、多 3 个依赖不划算。

**代价**
- 放弃 PyMuPDF 的表格能力（将来要做再引 pdfplumber，且只在 worker 内、按需按页调用）。
- **授权差异**：PyMuPDF 是 AGPL-3.0（商用需买授权），pdfplumber 是 MIT。本项目已开源，
  AGPL 合规（提供源码即可）；但若将来把 `dist\mech-qbank.exe` 作为闭源商品分发，需重新评估。
  这条需要 owner 明确接受。
- 上一轮我引用过「pdfplumber 在小样本上快 3–200 倍」，那是**测法有误**（跨进程、未预热）。
  本轮同进程公平对比已推翻：PyMuPDF 全面更快。此处更正。

### 【B】中文乱码：三条并联判据，U+FFFD 只占其中一条

**建议**：抽取后对每页文本做一次字符统计，三条判据任一命中即标 `garbled`，但**不阻断**。

| 判据 | 阈值 | 指向 |
|---|---|---|
| U+FFFD 替换符占比 | > 1% | 解码失败（ToUnicode 映射缺失） |
| U+0080–U+00FF（Latin-1 补充区）占比 | > 20% 且 CJK 占比 < 5% | 编码失配（mojibake） |
| 私用区 U+E000–U+F8FF 占比 | > 5% | 字体映射损坏 |

**理由**
- 实测证明「只用 U+FFFD」会**漏检**：编码失配件提取出 `»úÐµÉè¼Æ»ù´¡`，全是合法码点，U+FFFD 计数为 0。
  这类乱码在中文教材 PDF 里比 ToUnicode 缺失更常见（老扫描 OCR 后重排的产物）。
- 正常中文的基线很干净：CJK 占比 40–84%、U+FFFD 0、控制符 0、私用区 0。阈值余量充足。

**处理方式**
- 单页命中 → 该页 `status="garbled"`，正文照常返回，附 `quality_warnings:[{page, kind, ratio}]`。
- 全文命中页数 > 80% → 整体 `status="garbled"`，前端提示「文字疑似乱码，建议改用粘贴」。
- **不阻断**：乱码是质量问题不是失败，阻断会让用户连能看的部分都拿不到。

**代价**
- 多做一遍 O(n) 字符扫描（653 字级别，可忽略）。
- 阈值是经验值，**本目录暂无真乱码样本**（合成件只能证明判据方向，不能证明阈值），
  需要用真实坏 PDF 回填校准。这条要如实标注在实现里，不要写成「已验证」。

### 【C】双栏栏序：words 级「行聚类 → 行内切段 → 段归栏」

**建议**：实现如下四步（已实测验证）。
1. `get_text("words")` 取词级坐标（不是 `blocks`）。
2. 按 y 中心聚成行，容差 = 中位字高 × 0.5。
3. 行内按 x 排序，相邻词间隙 > `max(3×中位字高, 20pt)` 处切段。
4. 段按中心 x 与 gutter 比较归栏（gutter = 出现频次最高的宽间隙位置），
   先输出左栏全部段（栏内按 y），再输出右栏。

**理由（实测对照）**
- 朴素 `get_text()` 在 02 样本上**是对的**（内容流按栏顺序写），但在硬样本上
  **完全串行**（右栏首行出现在偏移 11，左栏末行在 638）。真实教材 PDF 两种都有，
  不能赌。
- 块级 x 聚类我试过，**不可用**：硬样本上 `get_text("blocks")` 返回的块被内容流合并，
  栏数判成 1（左栏块=0）。
- words 级四步法在两个样本上都正确：硬样本栏数=2、左栏 30 行连续、右栏从 330 起
  （左栏末行在 319）；02 样本栏数=2 且顺序正确。

**代价**
- 词级坐标比块级多 5–10 倍对象，500 页上会额外占内存（未单独测，估计 +30–60 MB）。
  缓解：**按页处理并即时释放**，不累积全文档 words。
- 单栏文档要能快速判定「非双栏」并回退到行聚类输出，否则会把正常单栏的段间距误切。
  判定条件：gutter 必须落在页宽 30%–70% 之间，且左右两侧段数都 ≥ 全页段数 20%，
  否则判为单栏。
- 三栏及以上不支持，会退化成两栏（首版接受）。

### 【D】表格：首版不做结构化，用 blocks 保行

**建议**：不做单元格结构，改用 `get_text("blocks")` 按行聚合，并在页级返回 `has_table: true` 提示人工核对。

**理由**
- 实测 `get_text()` 会把表格拆成散列（`'Q235B'` / `'7.85'` / `'212'` / `'235'` 各占一行），
  行关系全丢——这是**不可接受的可读性**。
- `blocks` 聚合能保住「一行一条记录」（`'Q235B\n7.85\n212\n235\n机架、转鼓、焊缝结\n'`），
  单元格内换行也保留（`焊缝结` + `构`），是可读的。
- 结构化（`find_tables`）代价太陡：500 页 +100.48s / +368 MB。首版不值得。

**代价**
- 列无标识，用户看到的是「一行 5 个值堆在一起」，需要自己对照表头。缓解：表格页在文本里
  显式插入 `[表格，建议对照原表核对]` 标记，前端高亮。
- 若将来要做结构化，走 pdfplumber 按需（用户点某页「解析表格」时才调），
  成本 1.89s / 260 MB 全量，单页则可忽略。

### 【E】页码：physical 必得，printed 用「众数偏移」校正

**建议**
- `physical_page`：页序索引，从 1 起，**永不失**，作为主键。
- `printed_label`：取每页**末行**和**首行**，用严格正则匹配纯页码模式
  （`^\s*[—\-–]\s*(\d+)\s*[—\-–]\s*$` 及 `第\s*(\d+)\s*页`），命中即候选。
- **两遍扫描**：先收集全部候选，算 `printed - physical` 的众数偏移；只有偏移一致率
  ≥ 80% 时才采纳 printed_label，否则全部置 null。
- 取不到 → `printed_label: null`，前端回落显示 `physical_page`。

**理由**
- 实测页脚 `— N —` / `- N -` 3/3 命中；无页码样本 01 末行是正文，不误判。
- 偏移场景实测：physical 1/2/3 → printed 12/13/14，偏移恒为 11。若直接用 physical
  当 printed，会指向错误页（差 11 页）。众数校正是必要的。
- 单页偶发命中不可信（页眉常有「第 3 章」这类字样），必须靠「连续多页偏移一致」把关。

**代价**
- 需要解析全部页的首末行，比只抽正文多一遍轻量扫描（每页 2 行，可忽略）。
- 页码在页眉、或与章节名混排（`3-1`）、或罗马数字（`xiv`）时取不到；首版接受 null。

### 【F】内存与进程模型：**必须独立 worker 子进程**

**建议**：解析放独立子进程，主进程只通过 stdio/临时文件收 JSON 结果。

**理由（基于实测，不是照抄）**
1. **固定开销 117 MB 不归还**：单页 2.3 KB 就到 139.2 MB，500 页 208.4 MB。
   Python/MuPDF 释放后 RSS 不回落，若在主进程，uvicorn 常驻 RSS 从几十 MB 永久涨到 200 MB+，
   用户机器上看就是「开过 PDF 之后越来越卡」。
2. **C 层崩溃会杀死整个服务**：MuPDF 是 C 库，畸形 PDF 可能 segfault，Python 的 `try/except`
   **抓不住**。本项目是 `--windowed` 单进程 exe，主进程一死用户只看到「页面打不开」。
3. **可设超时强杀**：实测 `find_tables()` 在 500 页上跑 100.83s，说明 C 层循环可以很久。
   主进程里无法中断，子进程可以 `terminate()`。
4. **可限制并发 1 + 文件大小上限**，避免内存叠加（两个 500 页并发就是 400 MB+）。

**代价（这里有本项目特有的打包陷阱，必须提前处理）**
- **frozen 下 `sys.executable` 是 exe 本身，不是 python**。所以 worker 不能写成
  `subprocess([sys.executable, "-m", "app.pdf_worker"])`——打包后这条命令会重新启动整个应用。
  正确做法：打包后的 exe 在 `main()` 入口检测 `--pdf-worker` 参数走 worker 分支
  （PyInstaller 会把 `sys.argv` 传进来），源码态才用 `-m`。
- **`--windowed` 下 `sys.stdout/stderr` 是 None**，worker 的 stdout 管道不可用。
  结果必须写临时文件（或命名管道），不能 `print` 回传。
- 进程启动开销约 0.2–0.3s（含 `import pymupdf`）。
- 需要处理 worker 超时、崩溃、僵尸进程回收，代码量比在主进程里调库多。

### 【G】三类边界（按 owner 已定口径落实）

| 情形 | 判定 | 行为 | 错误码 |
|---|---|---|---|
| `needs_pass=1` 且无口令 | 打开即检 | 拒，body 带 `needs_password: true`，前端弹口令框 | `encrypted_document` (422) |
| 提供口令但 `authenticate()` 返回 False | — | 拒，message 区分「口令错误」与「需要口令」 | `encrypted_document` (422) |
| `needs_pass=0` 但 `permissions` 禁复制 | `p & PDF_PERM_COPY == 0` | **允许抽取**，UI 提示「该文档声明禁止复制」 | 无（200） |
| 解析抛异常 | `FileDataError` 等 | 拒，worker 不崩、主进程不崩 | `corrupt_document` (422) |

**理由**
- 「禁复制」在 PDF 里是**权限位声明，不是技术封锁**：实测 `permissions=-3900`、`copy=False`
  的文件，`get_text()` 照样完整提取 18 字符，不需要任何绕过手段。
  用户处理的是自己的文件、本地运行、结果不外传，允许是合理的。
- `permissions` 是**负数**（-4 / -3900），必须用 `p & 常量` 判定，`== ` 比较会全错。
- 权限常量值是 4/8/16/32/256/512/1024/2048，**不是** `1<<i` 顺序——我第一版就按位序写错了，
  已用官方常量改正。

**代价**
- 口令要经 IPC 传给 worker，**不能落日志、不能进 request 日志**。需复用 `errors.SENSITIVE_KEYS`
  的脱敏（`password` 已在名单里）。
- UI 上「禁复制」提示属于法律措辞，建议用中性表述：「该文档声明禁止复制文本，仅用于个人学习摘录」。

### 【H】扫描件：`字符/页` + `图片覆盖率` 双判据

**建议**
- 判 `no_text` 的条件：`该页字符数 < 50` **且** `图片覆盖面积 / 页面积 > 0.5`。
- 命中即 `status="no_text"`，不报错，返回空文本 + 页码，前端提示「此页为图片，需手动粘贴或 OCR」。

**理由**
- 实测 04-scanned：字符 0、图片 1、覆盖率 **100.0%**；01/03：字符 653/260、图片 0、覆盖率 0%。
  两个维度都能干净分开。
- 不能只看「字符 = 0」：扫描页常有页眉/水印文字层（OCR 残留），字符数 10–40 但仍无法阅读。
  也不能只看「字符 < 50」：纯图页里夹一行图注会误判。两个条件并联才稳。
- 50 这个阈值取自「正常中文页 653 字符」的 1/13，留足余量。

**代价**
- `get_image_info()` 每页多一次调用（500 页实测含在 `get_text` 路径里，成本可忽略）。
- 阈值是经验值，需图文混排样本校准（当前 fixtures 只有纯扫描和纯文本两端，无中间态）。

### 【I】前端：约束可满足，零新增依赖

**建议**：PDF 抽取产物 = `{pages:[{physical_page, printed_label, text, status}], ...}`，
前端把它拼成「`[第 N 页]` + 正文」的纯文本段落，直接喂给现有 `ExcerptView` 的输入框。

**理由（对着现有代码确认过）**
- `ExcerptView` 的划词逻辑基于 `Range` 偏移，且段落 div 内**只放纯文本节点**，
  所以偏移永远准。PDF 抽取产物正好是纯文本，**零改动复用**。
- 现有流程是「粘贴/拖入文本 → 按空行拆段 → 划词 → `【N】` 占位」。PDF 只需多一步
  「把页分隔行插进去」，其余完全一致。
- **绝不引入 pdf.js**：它必须走 ESM + worker，会撞碎现有的 file:// 双闸
  （`format:'iife'` + `inlineDynamicImports` + `<script defer src>` 重写）。
  这条红线不能碰。

**满足度确认**：能。损失的是「原版式预览」——用户看不到表格线条、图片位置、分栏布局。
缓解手段：
- 每页开头插 `[第 N 页]` 锚点，与抽取出的 `printed_label` 并列显示（如 `[第 3 页 / 原文 p.12]`）。
- `status` 为 `no_text` / `garbled` / `has_table` 的页，在锚点后加标记，提示人工核对。

**代价**
- 扫描件完全无内容（本就无文本层），只能提示用户手动粘贴或后续接 OCR。
- 无版式信息意味着**表格摘录质量下降**（见【D】），这是首版的已知短板。

### 【J】两套服务端等价，且抽取库只被 worker 引用

**建议**（这里有个必须绕开的冲突）：
- **冲突**：新层（`storage`/`repository`/`service`）硬约束是**纯标准库**，而 PyMuPDF 是第三方。
  直接把 `import pymupdf` 写进 service 层，`server.py` 的零依赖回退当场失效。
- **解法**：抽取库**不进入任何被 import 的模块**，只作为 worker 进程入口。

```
app/pdf_worker.py      ← 唯一 import pymupdf 的文件，只作进程入口（python -m / exe --pdf-worker）
app/pdfclient.py       ← 纯标准库：subprocess + json + 超时 + 临时文件，service 层调它
app/service.py         ← 调 pdfclient，返回 Result；不认识 HTTP，不 import 第三方
app/api.py / server.py ← 各自把 Result 翻译成 HTTP（复用 _raise4xx / jerr）
```

**接口（两套服务端必须一致）**

| 方法 | 路径 | 请求 | 响应 |
|---|---|---|---|
| POST | `/api/v1/pdf/extract` | multipart 文件 或 `{"path": "..."}` | `{pages:[...], total_pages, status, quality_warnings, request_id}` |

- 两处都走 `service.extract_pdf(STORE, ...)`，业务逻辑只有一份。
- 两处错误体都由 `errors.error_body()` 组装，保证结构一致。

**验收方式（可自动化）**
- `grep -r "pymupdf" app/` 只应命中 `pdf_worker.py`。
- 在一个**没装 pymupdf** 的解释器里 `python -c "import app.service"` 必须成功
  （证明主路径不依赖第三方）。
- `start.bat` 的回退路径（fastapi 不可用 → `server.py`）仍要能启动，且
  `/api/v1/pdf/extract` 在 pymupdf 缺失时返回 `unsupported_type` 或专用码，**不崩**。

**代价**
- 多一个 `pdfclient` 模块和一层 IPC；调试链路变长（错误要跨进程回传）。
- frozen 打包要在 `spec` 里包含 worker 分支（见【F】）。

### 【K】错误码扩展：加 2 个，且必须同时改三处

**建议**

```python
CODE_STATUS = {                      # 现有 7 个保持不变
    'invalid_param': 400,
    'not_found': 404,
    'unauthorized': 401,
    'forbidden': 403,
    'internal_error': 500,
    'payload_too_large': 413,
    'unsupported_type': 415,
    # 新增
    'encrypted_document': 422,       # 需要口令 / 口令错误
    'corrupt_document': 422,         # 结构性损坏，无法解析
}
```

**扩展方式（三处都要改，缺一处就退化成 500）**
1. `app/errors.py` 的 `CODE_STATUS` 加两个键——`error_body()` 会自动拾取。
2. `app/api.py` 的 `_raise4xx()` 加 reason → code 的映射（现在只认 `not found` 和 `'error'`→400）。
3. `app/server.py` 的 `jerr()` 侧同步加；`tools/smoke_api.py` 加断言。

**为什么选 422 而不是 401/400**
- 401 现有语义是「调用方身份无效」，而「PDF 需要口令」不是身份问题。
- 400 已被 `invalid_param` 占用（参数格式错）。422 表示「格式对但内容无法处理」，
  正好对应「确实是 PDF，但打不开」。

**陷阱（必须写进实现注释）**
- `error_body()` 里有一行 `c = code if code in CODE_STATUS else DEFAULT_CODE`——
  **未知 code 会静默降级成 `internal_error`**。所以只加 `_raise4xx` 分支、忘了加
  `CODE_STATUS`，前端会收到 `500 + code=internal_error`，排查时会绕大远路。
- `no_text` / `garbled` / `has_table` **不是错误码**，是 `200` 响应里的 `status` 字段，
  不要塞进 `CODE_STATUS`。

## 3. 你点名的两个问题

### 3.1 怎么判定一个 PDF 属于「损坏」而非「空文档」

**答案：看 `doc.is_repaired`，不要看文本是否为空。**

实测依据见 §1.4：
- 正常样本（01–04）`is_repaired = False`；扫描件 04 也是 `False`——它是**合法文档，只是没有文本层**。
- 结构性损坏的软损坏区（截断 35%–99%）`is_repaired` **恒为 `True`**，
  **包括截断 95% 已能提取 653 字符（与完好件等量）的那一档**。
  这证明它比「文本是否为空」可靠得多。
- 截断 10%–30% 直接抛 `FileDataError`，走硬失败分支。
  （5% 那一档会被当成无 xref 老式 PDF 修复成功，属异常档，不代表「损坏可恢复」。）

**建议的判定链（顺序不能换）**
```
try open()
  ├─ 抛 FileDataError / RuntimeError   → corrupt_document (422)，无内容
  └─ 成功
       ├─ needs_pass → 口令流程（见【G】）
       ├─ is_repaired == True          → corrupt_document (422) + 附已抽取文本 + repaired=true
       ├─ 字符/页 < 50 且 图片覆盖率 > 0.5 → 200, status="no_text"
       ├─ 字符/页 < 50 且 无图无矢量      → 200, status="empty"
       └─ 其余                          → 200, status="ok"
```

**一个需要你拍板的取舍**：`is_repaired=True` 时是「拒」还是「降级返回」？
- 我建议**降级返回**：`200 + status="repaired"` + `repaired: true` + 已抽到的文本，前端显著提示。
  理由：95% 截断那档文本其实是完整的，直接拒会让用户白丢一份可用文档；
  而 35% 那档文本为 0，用户看到提示自然会换文件。
- 若要严格按「损坏就拒」的口径，则 `is_repaired=True` 一律 422 `corrupt_document`。
